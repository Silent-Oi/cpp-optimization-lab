## 可观察性与可视化

本节用于回答“这个项目最终怎样被看见”，不等于所有项目都必须建立窗口、动画或独立 visualizer，也不规定统一目录、库或 target 名称。公共基础设施、纯工具实验或可视化没有额外价值的微型实验，可以明确记录不实现独立运行时可视化的理由。

- 最值得观察的状态、过程或结果：
- 主要目的：理解 / 调试 / 交互实验 / 结果表达 / 项目展示
- 第一版形式：结构化输出 / 静态图 / 动画 / 交互程序 / 最终图像 / 明确不需要
- 最小可观察产物：
- 项目结束时希望留下的可观看成果：
- visualizer 或结果输出怎样复用核心计算接口：
- 是否需要只读接口、状态快照、采样或数据导出；怎样保持原计算含义：
- 绘制、窗口事件、帧率限制、截图和交互怎样与 benchmark 计时隔离：
- 本项目自然引入的有限图形学知识：
- 明确不在本项目范围内的图形技术：
- 运行结果和展示证据的存放位置：
- 可视化完成时的可检查证据：

规划职责时保持以下边界：`core` 保存计算模型、算法和数据，`tests` 负责自动正确性与回归验证，`benchmark` 隔离绘制和交互后测量核心性能，`visualizer` 只调用核心接口完成展示与交互。不得为 visualizer 复制第二套算法。

## 范围边界

图形学内容也必须遵守知识预算。复杂 GUI、GPU API、第三方图形库和通用渲染框架只有在目标明确且满足进入条件时才考虑；可视化范围不能无限扩张并吞掉项目的主学习目标。

## 项目完成标准

- [ ] 核心计算结果正确且有独立验证。
- [ ] benchmark 可以在记录的环境中复现。
- [ ] 至少一个优化结论有明确证据。
- [ ] 能解释主要瓶颈和未采用方案的原因。
- [ ] 对适合可视化的物理或数值项目，存在至少一个与核心计算解耦、能够直接观察结果的产物；基础设施或明确不适合的项目已记录不实现的理由。
- [ ] 可视化的完成证据和存放位置明确，且没有用视觉观察代替正确性或性能证据。
- [ ] 已记录可迁移到下一项目的经验。
