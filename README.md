# C++ Optimization Lab

这是一个以物理与数值计算问题为载体、以 C++ 性能优化和计算机底层理解为核心的长期学习仓库。

项目不以代码量、功能数量或“使用了多少高级技术”衡量完成度，而以能否建立可信结果、可靠测量和可解释结论衡量学习成果。

## 长期学习目标

通过一系列计算过程清晰、性能压力明显且结果可以验证的子项目，逐步建立以下能力：

- 把物理或数学问题转化为明确的状态、参数、算法和数据结构。
- 理解离散方法、初始条件、边界条件、稳定性、误差与收敛性。
- 把计算状态、演化过程和最终结果转化为可以直接观察的表达，用于理解、调试、交互实验和体验亲手实现的成果，而不只是展示包装。
- 随项目需求逐步学习数据映射、动画与交互、软件绘制、图形 API、GPU 绘制和渲染系统中的有限新知识。
- 在真实数值程序中理解对象、引用、指针、生命周期、RAII 和标准容器。
- 理解连续内存、数据布局、缓存、分支、向量化、线程调度和内存带宽如何影响 CPU 性能。
- 建立正确性基线、可复现 benchmark，并使用证据判断优化是否有效。
- 解释速度、内存、精度、复杂度、可读性和可维护性之间的权衡。

本项目的中期目标是完成稀疏矩阵与二维 Poisson 方程求解器，掌握 CSR、SpMV、共轭梯度法、简单预条件和 matrix-free 方法。

最终综合目标仍是完成具备三角形网格、BVH 和多线程能力的高性能 CPU 路径追踪器，把数学、物理、算法、数据结构、现代 C++ 和 CPU 优化能力连接起来。前期并行积累的可观察性、数据映射和图形学经验将逐步为这一目标提供基础。

## 核心学习闭环

每个子项目都应遵循同一条主线：

1. 明确问题边界和数学模型。
2. 实现简单、清晰、可信的正确版本。
3. 建立独立的正确性验证。
4. 建立可复现的性能基准。
5. 使用测量或工具识别实际瓶颈。
6. 提出一个明确的优化假设。
7. 一次只改变一个主要因素，重新验证并测量。
8. 记录结论、限制和可迁移到后续项目的经验。

不得仅凭经验断言某种写法更快，也不得以牺牲数值可靠性或结果一致性换取表面速度。

## 两条相连但职责独立的能力线

仓库的主线保持为“问题建模—可信 baseline—独立正确性验证—可复现 benchmark—瓶颈证据—受控优化实验—结论与能力迁移”。

与它并行发展的辅助能力线是“可观察性、可视化与图形学”：从结构化文本、CSV 和静态结果起步，逐步进入静态图像、实时动画、交互观察、CPU 软件绘制、科学数据可视化、按需使用图形 API 与 GPU 绘制，最后汇入 CPU 光线追踪和路径追踪系统。具体递进见 [`docs/roadmap.md`](docs/roadmap.md)。

两条能力线可以在同一项目中通过核心计算接口相连，但不互相替代，也不要求同步推进：

- 可视化不是每次 benchmark 前的统一阻塞步骤，也不把复杂 visualizer 设为进入下一性能项目的硬门槛。
- 可视观察可以帮助形成直觉、发现异常和设计实验，但不能代替自动测试、解析或参考结果、收敛规律和性能数据。
- 具有明确物理状态、空间结构、时间演化或最终图像的项目，原则上应认真回答“这个项目最终怎样被看见”，并留下与项目规模匹配的最小可观察成果。
- 公共基础设施、纯构建或工具实验，以及可视化没有额外理解、调试或表达价值的微型实验，可以明确记录“不需要独立运行时可视化”的理由。

## 子项目规划契约

后续每个子项目都必须说明：

- **路线定位**：承接了哪些已有能力，将为哪个后续项目提供基础。
- **核心问题**：要完成的物理、数学或算法问题是什么。
- **知识预算**：本项目重点引入哪些有限的新知识，不把所有相关主题一次塞入。
- **范围边界**：核心范围、条件触发的可选实验，以及明确不做的内容。
- **正确性证据**：解析解、参考解、守恒量、收敛规律或交叉实现中的哪一种。
- **性能问题**：准备验证哪个具体性能假设，而不是笼统追求“更快”。
- **可观察性与视觉成果**：哪些状态、过程或结果值得观察，最小可观察产物和项目结束时的可观看成果是什么；若不需要独立运行时可视化，应说明理由。
- **里程碑**：每个里程碑的产物、验证证据和需要真正理解的概念。
- **完成标准**：代码、正确性、性能结论、条件适用的可观察成果和学习总结分别达到什么状态。

规划时遵守以下约束：

- 只详细展开当前里程碑和紧邻的下一里程碑；更远阶段保留粗粒度目标。
- 正确性测试随功能一起建立，不集中拖到项目末尾。
- 在可信 baseline 和瓶颈证据出现前，不进入手动 SIMD、线程池、无锁结构等复杂优化。
- 可选实验必须有明确进入条件；没有证据支持时可以不做。
- 图形学内容同样遵守知识预算，不默认引入复杂 GUI、GPU API、第三方图形库或通用渲染框架。
- 子项目不追求过早通用化。只有至少两个项目已经出现稳定重复需求，或明确属于通用实验或展示基础设施的内容，才进入 `Project00_common`。

新建或重构子项目时使用 [`docs/project_planning_template.md`](docs/project_planning_template.md)。

## 计算、验证、测量与展示边界

子项目根据实际需要设置 target 和目录，不要求统一命名，但职责应保持以下边界：

```text
core       -> 计算模型、算法和数据
tests      -> 自动正确性与回归验证
benchmark  -> 隔离绘制和交互后的正式性能测量
visualizer -> 调用核心接口，读取或采样计算结果并完成展示与交互
```

- visualizer 复用核心计算接口，不复制或维护第二套算法。
- 核心计算不依赖窗口、输入、帧率、绘制或具体图形库；图形依赖尽量只属于展示相关 target。
- 绘制、窗口事件、帧率限制、截图和交互不进入核心 benchmark 的计时范围，visualizer 的帧率也不能直接作为核心计算性能结论。
- 展示可以抽样、聚合或进行坐标映射，但必须保留并说明被展示数据的计算含义。
- 若展示需要只读接口、状态快照或数据导出，应将其记录为明确设计决定，不把绘图代码渗入核心循环，也不为画图破坏核心数据职责。
- 不因未来可能复用而提前建设通用窗口层、渲染器、场景系统、UI 框架或图形抽象层。
