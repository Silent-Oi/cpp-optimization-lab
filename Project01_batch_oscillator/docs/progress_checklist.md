# M3 — Benchmark 与瓶颈证据

目标：为 M2 的单线程 AoS baseline 建立可复现的 Release benchmark，观察吞吐量随数据规模的变化，并形成第一条由测量支持、可以被后续实验否定的瓶颈假设。本阶段不修改数据布局或核心算法。

## Benchmark 边界

- [x] 在 `benchmarks/` 建立独立的 AoS benchmark 入口和 CMake target。
- [x] 保留现有 `oscillator_batch` 作为 M2 功能/压力示例；benchmark 不复制或改写 `update_aos_batch()` 的核心算法。
- [x] benchmark 直接复用 `make_OscillatorAoS_batch()`、`update_aos_batch()` 和 `aos_batch_report()`。
- [x] 本项目先在 benchmark 驱动中直接使用 `std::chrono::steady_clock`，不因单个项目提前实现 `Project00_common` 的通用 timer。
- [ ] 使用 Release、单线程和固定编译选项运行正式测量。
- [x] 计时区间只包含 `update_aos_batch(working_batch, steps)`；初始化、工作副本准备、结果汇总和输出全部在计时外。

## 测量设计

- [x] 先测量 `N = 1,000`、`10,000`、`100,000`、`1,000,000` 作为宽范围扫描；若相邻规模之间出现明显吞吐量变化，则在该区间增加规模以定位变化范围。
- [ ] 根据 `sizeof(OscillatorAoS)` 和当前 CPU 缓存容量，至少补充一个能够代表较小缓存内工作集的规模；具体规模和选择理由记录在报告中。
- [x] 固定相同的 `seed`、`dt`、参数分布和更新语义；每个规模的 `steps` 在正式测量前确定，并在该规模的全部重复中保持不变。
- [x] 允许不同规模使用不同 `steps`，使单次计时达到足够稳定的持续时间；记录实际 `N × steps`，所有吞吐量均使用实际总更新数计算。
- [ ] 用不计入正式结果的校准运行确定各规模 `steps`，避免小规模计时过短。
- [x] 每个规模只生成一次 `initial_batch`；每次预热或正式测量前，在计时外复制得到 `working_batch`。
- [x] 预热使用独立工作副本且不计入结果；正式测量至少重复多次，每次都从相同初始状态开始。
- [x] 每次记录 `N`、`steps`、总更新数 `N × steps`、总时间、每秒更新数、每振子每步耗时。
- [ ] 每次计时结束后调用现有 `aos_batch_report()`，记录 `state_checksum`、`max_abs_x`、`max_abs_v` 和 `finite`。
- [x] 保存每次原始测量，不只保留最快一次。
- [ ] 每个规模正式测量至少 7 次，以中位数作为代表值，同时报告最小值、最大值和相对波动范围。
- [ ] 记录 CPU、编译器、Release 配置、运行命令和影响复现的环境条件。

## 正确性与可复现性

- [x] 同一规模的全部重复得到一致且有限的 `AoSResults`。
- [x] `aos_batch_report()` 在计时后消费最终状态，使核心更新结果保持可观察，避免计算被编译器消除。
- [x] 吞吐量分母使用实际的 `N × steps`，时间单位转换与输出字段能够独立核对。
- [ ] 原始输出保存在 `results/`，正式结论不只存在于被忽略的原始文件中。

## 初步瓶颈证据

- [ ] 记录当前编译器下的 `sizeof(OscillatorAoS)`；核对当前结构由 8 个 `double` 组成，并计算各规模的 `N × sizeof(OscillatorAoS)` 工作集。
- [ ] 把各规模工作集与当前 CPU 的 L1、L2、L3 容量联系起来，但不把“超过缓存容量”直接当成已证明的原因。
- [ ] 根据现有核心循环记录每次更新的源码级工作：读取 `position`、`velocity` 和 4 个矩阵系数，写回 2 个状态量，执行 4 次乘法和 2 次加法。
- [x] 单独指出 `omega`、`zeta` 保存在每个 8-double AoS 元素中但不被热循环使用，区分结构体步长与源码显式读取字节。
- [ ] 区分源码级读写估算、缓存行传输和实际内存带宽流量，不用简单字节相加替代硬件证据。
- [ ] 比较不同规模的吞吐量与波动，指出性能变化出现在哪些规模区间。
- [x] 区分“测量现象”“基于现象的推断”和“尚未证明的原因”。

## 可选主题的进入条件

以下内容不计入核心进度：

- **RK4**：需要比较通用高阶积分方法，而不是为了补齐方法列表。
- **完整收敛阶实验**：需要进一步验证积分器理论阶数时再做。
- **手动 SIMD**：自动向量化不足、核心循环仍为计算瓶颈，且复杂度具有学习价值。
- **临界/过阻尼**：后续问题明确需要覆盖不同阻尼区间。
- **线程池**：至少两个项目出现重复线程调度需求后，再考虑进入 Common。
