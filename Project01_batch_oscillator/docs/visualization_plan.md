# Project01 V1 可视化专项规划

## 文档职责与当前状态

本文是 V1 实施路线的唯一详细来源。Project01 README 只说明成果与边界，`design.md` 只保留已经接受的决定及理由，`progress_checklist.md` 只记录粗粒度状态。

V1 当前尚未开始。本规划不表示 visualizer target、图形依赖或计划目录已经存在，也不改变 M3、M4 的性能证据门槛。

## 目的与项目定位

V1 的目的，是把 Project01 已有的批量振子状态转化为可直接观察的二维画面，让学习者建立从数值状态、确定性抽样到像素表示的完整认识。它是 Project01 的核心可观察成果，但 Project01 的主要学习方向仍是批量数值更新与 CPU 性能优化。

架构上，V1 与性能实验相互独立；实际学习执行时，同一时期只保持一个活动里程碑。当前建议顺序为：

```text
M3 Benchmark 与瓶颈证据
    → M4 数据布局与编译器实验
    → V1 实时振子点阵
    → M6 项目整理与能力迁移
```

若后续条件性能实验 M5 被证据触发，可根据当时上下文安排，但不与 V1 同时推进。V1 不降低或替代任何正确性、benchmark、实验报告或性能结论门槛。

## 最终最小成果

V1 的最终成果是：使用现有核心接口推进完整 batch，并以固定、均匀、可复现且覆盖整个 batch 的显示索引，实时绘制确定性抽样的振子点阵。

计算数量与显示数量必须分离：

```text
计算数量：完整 batch 中的全部振子
显示数量：与窗口和网格容量匹配的代表样本
```

显示端不能通过只计算被画出的样本来降低工作量，也不能默认只取 batch 开头的若干元素。单振子画面只是验证核心接入和坐标映射的中间步骤，不是最终成果。

点阵采用固定视觉语义：

- 屏幕划分为规则网格，每个单元对应一个抽样振子。
- 单元中心表示平衡位置，`position` 映射为单元内的水平偏移。
- `velocity` 的方向和大小映射为颜色或亮度。
- 抽样、缩放和颜色映射只改变表示方式，不改变核心状态的计算含义。

## 模块职责边界

| 模块 | 唯一职责 | V1 边界 |
|---|---|---|
| `oscillator_core` | 保存物理模型、状态、参数和批量更新算法 | 不依赖 RGFW、窗口、像素、输入事件或帧率；不为显示维护第二套状态 |
| tests | 验证核心计算的正确性与回归行为 | 画面“看起来正确”不能替代自动测试 |
| benchmark | 在固定条件下测量核心计算 | 初始化、绘制、事件轮询、帧率限制、截图和交互不进入正式计时 |
| visualizer | 调用 `oscillator_core`，管理抽样、映射、窗口、像素缓冲和交互 | 不复制振子公式，不承担 AoS/SoA、向量化或线程扩展性结论 |

visualizer 应优先复用现有批量初始化和更新接口。只有实际实现证明现有只读访问不足时，才讨论最小的核心观察接口；规划阶段不预先设计 snapshot 框架或通用展示抽象。

visualizer 帧率只能描述展示体验，不能形成核心计算性能结论。正式性能结论继续来自独立 benchmark 和可复现实验记录。

## 第一版技术路线

- 使用 RGFW 负责窗口创建、输入事件和 CPU 像素表面的显示。
- visualizer 自己维护 CPU RGBA 像素缓冲，完成清屏、像素写入和少量简单图元的软件绘制。
- 通过 `RGFW_surface` 与窗口 blit 显示像素缓冲；第一版不引入 GPU 绘制管线。
- RGFW implementation 只在一个 visualizer 翻译单元中实例化，不进入 `oscillator_core` 或 `Project00_common`。
- 开始实施 V1 时固定 RGFW 版本或 commit，并保留对应许可证。具体导入方式在 V1 成为当前里程碑时决定。

## 模拟时间与显示时间

V1 必须分别管理并解释以下概念：

- 固定物理时间步 `dt`。
- 核心模拟推进的次数。
- 现实经过时间。
- 画面刷新频率。

第一版可以从每次刷新推进固定步数开始，但不能让显示器刷新率静默改变模拟时间语义，也不能为了维持帧率修改核心物理公式。V1 完成前应理解固定时间步 accumulator 如何把现实时间转换为零次或多次固定 `dt` 推进。

## 最小交互

- `Space`：暂停与继续。
- `Right Arrow`：暂停时单步推进。
- `R`：使用相同 seed、参数和规模重置。
- `Escape`：退出。

第一版不增加其他交互要求。

## 未来构建隔离决定

`oscillator_visualizer` 应通过独立构建选项控制，建议命名为 `CPP_LAB_BUILD_VISUALIZERS`，默认 `OFF`。

该选项只影响 visualizer 与图形依赖，不影响 core、apps、tests 和 benchmark。本节只记录未来决定；V1 开始前不修改 CMake，也不创建 target。

## 展示素材策略

- 一张能够辨认振子点阵、位置偏移和速度映射的 PNG 是 V1 的核心展示证据。
- GIF 或短视频是可选增强，不是核心完成门槛。
- 提交到普通 Git 历史的动态素材建议不超过 10 MiB。
- 更大的动态素材不进入普通 Git 历史，可保存在仓库外或其他适合的大文件存储中，并在文档中记录获取方式。
- 正式运行素材计划放入 `docs/showcase/`；设计图仍放在 `docs/diagrams/`，学习过程附件仍由学习者放在 `docs/learning_logs/<里程碑>/assets/`。

## 高层实施顺序

V1 成为当前里程碑后，按以下顺序推进：

1. 最小窗口与像素表面。
2. 软件像素写入与简单图元。
3. 单振子接入与坐标映射。
4. 完整 batch 与抽样点阵。
5. 最小交互与展示证据。

V1 尚未开始时不把这些阶段展开为更细的 checklist。进入 V1 后，只详细展开当时的当前阶段和下一阶段。

## 明确不做与条件扩展

V1 核心范围不包括：

- GUI 框架、字体系统、菜单、滑块或复杂参数编辑。
- 多窗口、通用 renderer、scene、window wrapper 或图形抽象层。
- OpenGL、Vulkan、DirectX、shader 或其他 GPU API 路线。

只有实时振子点阵已经完成且仍有明确学习价值时，才讨论相空间轨迹、阻尼对比、位移或能量曲线、额外颜色映射、复杂参数编辑或 GPU 绘制等扩展。

## 实施开始时再决定

以下内容留到 V1 成为当前里程碑时确定：

- RGFW 的固定版本或 commit、许可证副本位置和具体导入方式。
- 默认窗口大小、完整计算规模、显示样本数和映射常量。
- 每次刷新推进步数及 accumulator 的具体组织方式。
- 实际源码文件名、target 定义和构建运行命令。
