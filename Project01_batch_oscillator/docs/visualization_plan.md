## 目的与项目定位

V1 的主要目标不是展示 AoS、SoA、吞吐量或“程序一次能够更新多少振子”，而是把 Project01 研究的对象——大量独立欠阻尼振子——转化为具有明确物理含义的动态画面。

可视化应直接表现以下动力学特征：

* 振荡对应相空间中的旋转。
* 固有角频率 `omega` 决定相位推进速度。
* 阻尼比 `zeta` 决定振幅衰减速度。
* 不同参数的振子经过一段时间后产生相位剪切、结构展开和不同速度的向平衡态收缩。
* 所有欠阻尼振子最终趋向相空间原点。

V1 应同时具备两种价值：

1. **物理表达**：观众能够从画面中看出振荡、频率差异、阻尼衰减和平衡态。
2. **视觉表现**：画面应具有足够鲜明的动态结构，可以作为 Project01 的代表性展示成果。

Project01 的主要学习方向仍然是批量数值更新与 CPU 性能优化。V1 是研究对象的可视化表达，不替代正确性测试、benchmark 或性能实验。

实际学习顺序保持为：

```text
M3 Benchmark 与瓶颈证据
    → M4 数据布局与编译器实验
    → V1 实时可视化
    → M6 项目整理与能力迁移
```

若 M5 条件并行实验被证据触发，应根据当时上下文单独安排，不与 V1 同时施工。

## 核心成果：阻尼振子相空间星云

V1 的核心完成成果是一个由真实批量振子状态驱动的实时相空间星云。

每个被显示的振子对应相空间中的一个发光粒子：

```text
水平坐标：position
垂直坐标：velocity / omega
```

使用 `velocity / omega` 而不是直接使用 `velocity`，是为了让位置和纵向状态具有相近的尺度，并减少不同 `omega` 对相空间几何比例的直接拉伸。该映射只用于显示，不改变核心状态和物理计算。

在该画面中：

* 单个无阻尼振子会围绕原点形成闭合旋转。
* 欠阻尼振子会沿螺旋轨迹逐渐靠近原点。
* 不同 `omega` 会产生不同的旋转速度和相位剪切。
* 不同 `zeta` 会产生不同的收缩速度。
* 大量振子共同形成旋转、展开并逐渐坍缩的星云结构。

画面使用深色背景、发光粒子和短暂拖尾。拖尾用于显示运动方向和相空间轨迹，使振子的旋转与衰减能够被直接观察。

拖尾属于显示效果，不是额外的物理状态。第一版可通过每帧对旧像素进行衰减，而不是保存每个振子的完整历史轨迹。

## 核心展示场景

为了使不同物理因素能够被清楚观察，V1 至少准备一个确定性的展示场景。推荐优先实现以下两个场景，但核心完成门槛只要求其中一个达到正式展示质量。

### 场景 A：频率剪切星云

固定或小范围变化 `zeta`，让 `omega` 在一定范围内连续变化。

* 所有振子使用相同或有组织的初始状态。
* `omega` 决定粒子的颜色。
* 不同振子以不同速度围绕原点旋转。
* 初始集中结构会逐渐产生相位差，展开为旋臂、环带或花瓣状星云。
* 阻尼使整个结构最终向原点收缩。

该场景主要展示：

* `omega` 对相位推进速度的影响。
* 大量独立振子产生的相位混合与整体几何结构。
* 振荡与阻尼同时存在时的动态演化。

### 场景 B：阻尼坍缩星云

固定或小范围变化 `omega`，让 `zeta` 在欠阻尼范围内连续变化。

* 所有振子使用相同或有组织的初始状态。
* `zeta` 决定粒子的颜色。
* 不同振子以接近的角速度旋转，但以不同速度向原点收缩。
* 低阻尼粒子长时间保留较大轨道，高阻尼粒子更快集中到中心。

该场景主要展示：

* `zeta` 对振幅衰减速度的影响。
* 大量振子以不同速率趋向平衡态的过程。
* 阻尼系统相空间轨迹的螺旋收缩。

## 增强视图：参数梯度发光幕布

在相空间星云完成后，V1 增加一个参数梯度幕布视图。

该视图将振子按照某个参数顺序排列：

```text
屏幕水平位置：振子索引或参数位置
屏幕垂直偏移：当前 position
```

相邻振子的当前位置可以用发光线段连接，形成连续曲线或幕布。

推荐两种模式：

### `omega` 梯度幕布

* 从左到右连续增加 `omega`。
* 固定或小范围变化 `zeta`。
* 所有振子从相同初始状态开始。
* 不同频率逐渐产生相位差，曲线从整齐状态演化为密集波纹和相位纹理。

### `zeta` 梯度幕布

* 从左到右连续增加 `zeta`。
* 固定或小范围变化 `omega`。
* 各区域以不同速度失去振幅。
* 画面从低阻尼区域的持续振荡，连续过渡到高阻尼区域的快速平静。

相邻点之间的连线只用于视觉表达。所有振子在物理模型中仍然彼此独立，不表示振子之间存在弹簧、波传播或其他耦合关系。

参数梯度幕布用于回答：

> 当一个振子参数连续变化时，整组独立振子的运动形态如何连续改变？

## 可视化批量与性能批量的关系

V1 使用与 Project01 相同的振子状态、参数和批量更新算法，但不要求每个画面都使用 M3 benchmark 的百万规模。

两者目标不同：

```text
benchmark batch：
追求固定条件、稳定测量和可比较的性能数据。

visualization batch：
追求足够的视觉密度、清楚的动力学结构和稳定的实时显示。
```

可视化规模由画面密度、软件绘制成本和实际运行稳定性决定。它可以是数千、数万或更多振子，但不能通过修改物理公式来维持帧率。

当完整计算数量高于实际绘制数量时，可以使用固定、均匀且可复现的索引抽样。抽样只减少绘制粒子数量，不改变核心 batch 的更新语义。

V1 可以使用专门设计的确定性初始条件和参数分布，以产生清楚的频率剪切或阻尼梯度。它不必复用 benchmark 的随机输入，但必须继续使用相同的核心动力学实现。

## 视觉映射原则

可视化中的每一种视觉变化都应具有稳定含义。

### 相空间星云

推荐默认映射：

* `position`：粒子水平位置。
* `velocity / omega`：粒子垂直位置。
* `omega` 或 `zeta`：粒子颜色。
* 当前振幅、速度或归一化能量：粒子亮度。
* 过去若干帧的像素衰减：短拖尾。

一个画面中只选择一个参数作为主要颜色语义，避免同时使用复杂颜色编码表达多个变量。

### 参数梯度幕布

推荐默认映射：

* 参数顺序：整体水平位置。
* `position`：垂直偏移。
* `velocity` 的方向或大小：颜色或亮度。
* 相邻振子连接：连续发光曲线。

### 坐标稳定性

第一版应使用固定或由初始条件确定的显示范围，不应每帧根据当前最大值自动缩放。

逐帧自动缩放会让正在衰减的振子在画面上保持相似振幅，掩盖阻尼导致的真实收缩。

超出显示范围的粒子可以裁剪或限制到边界，但不得通过修改核心状态来适应窗口。

## 模块职责边界

| 模块                | 唯一职责                          | V1 边界                           |
| ----------------- | ----------------------------- | ------------------------------- |
| `oscillator_core` | 保存物理模型、状态、参数和批量更新算法           | 不依赖 RGFW、窗口、像素、颜色、输入事件、拖尾或帧率    |
| tests             | 验证核心计算的正确性与回归行为               | 画面“看起来正确”不能替代自动测试               |
| benchmark         | 在固定条件下测量核心计算                  | 初始化、绘制、事件轮询、拖尾、截图和交互不进入正式计时     |
| visualizer        | 构造展示场景，调用核心更新，完成映射、窗口、软件绘制和交互 | 不复制振子公式，不承担 AoS、SoA、向量化或线程扩展性结论 |

visualizer 应优先复用现有核心数据类型和批量更新接口。

若当前接口无法构造所需的确定性参数梯度，可以增加最小的初始化接口或在 visualizer 中构造核心数据对象，但不得维护第二套状态更新公式。

只有实际实现证明现有只读访问方式不足时，才讨论最小观察接口。规划阶段不建设 snapshot 框架、通用 renderer、scene 系统或图形抽象层。

## 第一版技术路线

* 使用 RGFW 创建窗口、处理输入事件并显示 CPU 像素表面。
* visualizer 自己维护 RGBA 像素缓冲。
* 实现清屏、像素写入、简单发光点、线段和逐帧像素衰减。
* 通过 `RGFW_surface` 和窗口 blit 显示结果。
* 第一版不引入 GPU 绘制管线。
* RGFW implementation 只在一个 visualizer 翻译单元中实例化。
* RGFW 不进入 `oscillator_core` 或 `Project00_common`。
* 实施 V1 时固定 RGFW 版本或 commit，并保留许可证。
* 具体依赖导入方式在 V1 成为当前里程碑时决定。

第一版“发光”不要求真实光照、后处理或复杂模糊算法。可以通过以下简单方式获得：

* 一个振子绘制中心亮点和少量邻近低亮度像素。
* 对旧帧像素乘以固定衰减系数形成拖尾。
* 对多个粒子写入同一像素时采用饱和叠加。
* 使用有限的预设颜色表或简单连续插值。

## 模拟时间与显示时间

V1 必须分别管理并解释：

* 固定物理时间步 `dt`。
* 核心模拟推进次数。
* 现实经过时间。
* 画面刷新频率。
* 每次画面刷新之间执行的模拟步数。

第一版可以从每次刷新推进固定步数开始，但不能让显示器刷新率静默改变模拟时间语义，也不能为了维持帧率修改核心物理公式。

V1 完成前应理解固定时间步 accumulator 如何把现实时间转换为零次或多次固定 `dt` 推进。

拖尾衰减属于显示时间效果，不应进入振子的物理更新。

## 最小交互

核心交互保持简洁：

* `Space`：暂停与继续。
* `Right Arrow`：暂停时单步推进。
* `R`：使用相同参数、规模和初始条件重置。
* `Escape`：退出。

当两个视图均已实现时，可以增加：

* `1`：切换到相空间星云。
* `2`：切换到参数梯度幕布。

除视图切换外，第一版不要求菜单、滑块、鼠标编辑或复杂参数界面。

## 高层实施顺序

V1 成为当前里程碑后，按以下顺序推进：

1. 建立最小 RGFW 窗口和 RGBA 像素表面。

6. 完成暂停、单步、重置和稳定时间推进。
7. 保存正式截图并补充运行说明。
8. 在核心成果完成后，再实现参数梯度幕布。

V1 尚未开始时，不将这些步骤展开为更细的 checklist。进入 V1 后，只详细展开当前阶段和下一阶段。

## 核心完成门槛

V1 核心完成需要同时满足：

1. visualizer 通过独立 target 构建，不污染 core、tests 和 benchmark。
2. 画面由 `oscillator_core` 的真实批量状态驱动，没有复制振子更新公式。
3. 相空间星云能够清楚表现振荡旋转和阻尼收缩。
4. 至少一个确定性展示场景能够稳定复现。
5. 坐标、颜色和拖尾的物理含义已经记录。
6. 暂停、单步、重置和退出可以正常工作。
7. 已保存至少一张正式截图并记录构建、运行方式。
8. 可视化帧率没有被当作核心计算性能证据。

参数梯度幕布属于推荐增强视图，但不阻塞 V1 核心完成。

## 明确不做

V1 核心范围不包括：

* GUI 框架、字体系统、菜单、滑块或复杂参数编辑。
* 多窗口。
* 通用 renderer、scene、window wrapper 或图形抽象层。
* OpenGL、Vulkan、DirectX、shader 或其他 GPU API。
* 粒子间相互作用、弹簧链或波动方程。
* 为了画面效果修改振子的物理更新公式。
* 用 visualizer 帧率替代正式 benchmark。
