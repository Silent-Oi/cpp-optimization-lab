# Project01 — Batch Oscillator 技术路线

> 百万级欠阻尼振子模拟、CPU 性能优化与相空间可视化。

Project01 研究同一个数值模型在不同数据布局、编译器优化和并行执行方式下的性能表现。

项目从正确的欠阻尼振子更新开始，将其扩展到百万级独立振子；随后围绕核心计算逐项优化，并使用统一 benchmark 对比每次改动；最终将振子状态绘制为实时相空间星云。

当前收尾顺序：**简单多线程 → 完成 Project01**。自动向量化阶段已完成；完成本项目后进入 Project02，CUDA 在下一项目的 CPU 热扩散版本验证后引入。

截至 2026-10-08，AoS/SoA 布局、AoS 对象大小、终止机制及自动向量化四组 benchmark 已有实现和结果，终止与活跃索引更新路径已实现。自动向量化阶段已完成编译器诊断、循环调整、核心汇编阅读，以及向量化与禁用向量化版本的性能对照。

正确性检查随实现改动进行，可复用现有参考结果或小规模对照，不以先建立独立测试套件作为进入多线程阶段的前提。终止边界的补充验证留到项目收尾，覆盖低能量退出、过平衡位置但能量仍高时继续更新，以及阈值以上无阻尼振子保持活跃。

## 项目目标

Project01 包含两个相互连接的目标：

1. **在 CPU 上高效更新大量欠阻尼振子；**
2. **将振子状态实时绘制为相空间星云。**

完整流程为：

```text
物理模型
→ 正确的标量更新
→ 批量计算
→ 经测量验证的 CPU 优化
→ 实时可视化
```

## 核心模型

每个振子满足：

```text
x' = v
v' = -2 * zeta * omega * v - omega^2 * x
```

当振子参数和时间步 `dt` 固定时，一步更新写成：

```text
x_next = m00 * x + m01 * v
v_next = m10 * x + m11 * v
```

`m00`、`m01`、`m10` 和 `m11` 在初始化阶段预计算，核心热循环只负责重复更新状态。

可视化使用归一化相空间坐标：

```text
horizontal = position
vertical   = velocity / omega
```

## 4. 数据布局优化

第一项优化是将 Array of Structures 基线改为 Structure of Arrays。

### 基线布局

```text
OscillatorAoS
├─ position
├─ velocity
├─ omega
├─ zeta
├─ m00
├─ m01
├─ m10
└─ m11
```

### 优化布局

```text
position[]
velocity[]
m00[]
m01[]
m10[]
m11[]
omega[]

```

更新循环只访问状态数组和更新系数数组。热循环不需要的参数仍然保留，但不再进入核心数据流。

### 工作内容

- 实现 SoA 批量初始化；
- 实现 SoA 单步和多步更新；
- 验证 AoS 与 SoA 结果一致；
- 使用现有 benchmark 比较两种布局；
- 根据实测结果理解数据布局对性能的影响。

### 结果


## 5. 编译器自动向量化

理解编译器如何在条件允许时使用一条指令同时处理多个振子。已有 SoA 循环能够自动向量化时，重点是阅读诊断、理解生成代码和剩余元素的处理，不要求为此新增一个实现。

本阶段以 `update_soa_batch_step_no_termination` 的连续更新循环为入口。Debug/Release 性能差异只作为观察线索，不能单凭耗时认定是否发生向量化；结论依据当前构建的编译器诊断，必要时辅以核心循环汇编。

### 工作内容

- 检查当前 Release 版本；
- 开启并阅读向量化诊断；
- 必要时检查生成的核心循环；
- 找出阻碍向量化的数据依赖、指针别名或控制流；
- 在有依据时简化循环或接口；
- 需要解释性能差异或确有代码改动时，复用现有 benchmark 进行对比。

主要目标是 SoA 更新循环：

```cpp
for (std::size_t i = 0; i < count; ++i)
{
    const double old_position = position[i];
    const double old_velocity = velocity[i];

    position[i] = m00[i] * old_position + m01[i] * old_velocity;
    velocity[i] = m10[i] * old_position + m11[i] * old_velocity;
}
```

手写 SIMD intrinsics 不属于本项目的完成要求。诊断显示未向量化时，只围绕明确原因做一次最小调整并验证；若仍受限，说明原因即可进入多线程阶段。

本阶段的完成边界是：能够区分 SIMD 与多线程、确认当前循环是否向量化，并解释一个实际促进或阻碍向量化的因素。已有自动向量化时，无需为增加代码量而另写一个版本。

### 结果

确认并理解现有循环的向量化行为；需要调整时再比较效果：

```text
SoA
→ 自动向量化
→ benchmark 对比
```

### 状态

**已完成**：已有自动向量化与禁用向量化的对照路径、benchmark 结果和图表。

## 6. 多线程更新

将优化后的单线程核心按连续振子区间分配给多个 CPU 线程。

```text
thread 0 → [0, begin1)
thread 1 → [begin1, begin2)
thread 2 → [begin2, begin3)
...
```

振子彼此独立，因此每个线程可以无锁更新自己的区间。

### 工作内容

- 实现连续区间划分；
- 使用 `std::thread` 或 `std::jthread`；
- 先完成两个线程的最小版本，理解数据归属、线程生命周期和等待完成；
- 验证单线程与多线程结果一致；
- 测试 1、2、4、8……线程；
- 计算加速比和并行效率；
- 找出继续增加线程不再带来有效收益的位置。

首个多线程版本复用无终止 SoA 连续更新路径，按不重叠区间分工；各线程完成后再读取结果。不并发修改共享的 `active_indices`。先完成正确性对照，再复用现有计时框架观察少量线程配置的收益与开销，不要求达到线性加速。

Project01 不实现通用线程池或任务调度系统，带终止路径的并行化不作为收尾要求。

本阶段的完成边界是：能够解释区间为何互不冲突、实现可配置线程数的更新、确认与单线程结果在约定容差内一致，并用少量测量说明线程数与问题规模对收益的影响。完成后进入项目收尾。

### 结果

完成第三项正式优化：

```text
最佳单线程版本
→ 简单多线程
→ benchmark 对比
```

### 状态

**计划中**

## 7. 振子终止与活跃状态

在明确的数值容差下识别可以停止演化的振子，退出后续更新和新点绘制，并使已有拖尾自然结束。判据应考虑完整状态，避免在经过平衡位置时误判；明确无阻尼情况、重置及活跃状态的处理。

按需要观察终止前后的实际计算与绘制成本。带终止的近似计算与原有固定步数基线分别说明语义，避免把减少计算量误认为相同工作量下的实现加速。

**终止更新与活跃索引管理已实现，已有性能实验；终止边界的独立正确性验证待补充。**
